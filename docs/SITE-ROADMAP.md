# План развития OldSchool Journal

Перенос блога на Django завершён. Решение для ближайшей версии — развивать OldSchool Journal как самостоятельный журнал. Ассортимент, доставка и оплата обсуждаются позже, когда появится конкретное направление продаж. Для будущего магазина сохранён [прототип витрины](STOREFRONT-PROTOTYPE.md).

## Ближайшие этапы журнала

| № | Что делаем | Как принимаем этап |
| --- | --- | --- |
| 1 | **Редизайн журнала.** Обновить главную, список статей и страницу статьи. Взять из прототипа тёплую палитру, тёмно-зелёный акцент и крупные заголовки. | На широком и узком экранах можно найти статью из меню, открыть полный текст и вернуться к списку. Главная показывает свежие статьи из базы. |
| 2 | **Испытательная версия.** Подготовить отдельный экземпляр Django с PostgreSQL, HTTPS, секретами вне Git и резервными копиями. Проверить настройки публичного запуска и защиту входа. | Сайт работает по HTTPS, проверки Django проходят, резервная копия восстановлена в отдельную базу. |
| 3 | **Подготовка первого выпуска журнала.** Определить темы и начальный набор статей, проверить редакторский процесс и публичные страницы. | Владелец может добавить статью через панель и открыть её из главной и списка. Проверены навигация, доступ и отображение ошибок. |

После каждого этапа проверяем результат, фиксируем его в Git и согласуем следующий этап. К каталогу возвращаемся, когда появятся реальные товары и условия продажи.

Этап 1 выполнен. На главной появилась обложка и до трёх свежих статей из базы. Список и страница статьи используют один стиль с главной. В браузере проверены переходы на широком экране и все три страницы при ширине окна 390 пикселей. [Результаты проверок](TESTING.md#редизайн-журнала)

Этап 2 выполнен на локальном стенде Windows. Сайт открывался по HTTPS, проверки Django для развёртывания завершились без ошибок с предупреждением о HSTS, копия восстановлена в отдельную PostgreSQL. Для размещения в интернете нужен хостинг и домен. [Результаты проверок](TESTING.md#испытательная-версия-журнала) · [Инструкция и задачи перед публикацией](STAGING.md)

Этап 3 завершён. Подготовлены три черновика выпуска «Город с блокнотом». В браузере проверены добавление статей через панель, чтение с главной и из списка, доступ гостя и читателя, возврат от страницы ошибки к статьям. Тексты готовы к редакторскому согласованию. [Черновики и порядок публикации](FIRST-ISSUE.md)

## Рекомендуемая архитектура

Один проект Django с отдельными приложениями по функциям. Такой подход называют модульным монолитом. Сайт запускается как одно приложение, а статьи, товары и заказы имеют свои модели, адреса и тесты. Текущие шаблоны Django можно развить в общий интерфейс для журнала и магазина.

| Часть | Что в ней |
| --- | --- |
| `entries` | Существующие статьи, города, погода и адреса для чтения данных. |
| `journal/accounts.py` | Существующие регистрация и вход. Здесь можно начать с восстановления пароля и подтверждения почты. |
| `catalog` | Категории, товары, варианты, фотографии и наличие. |
| `orders` | Корзина, оформление, позиции заказа, доставка и история статусов. |
| `payments` | Сессии оплаты, уведомления провайдера и возвраты. Понадобится при включении онлайн-оплаты. |

Для публичного сайта предлагается управляемая PostgreSQL — база данных, обслуживание и резервные копии которой предоставляет хостинг. SQLite можно оставить для быстрого запуска журнала на Windows и Mac. Настоящие сценарии заказов и проверку одновременных покупок нужно прогонять на PostgreSQL. Для фотографий использовать отдельное файловое хранилище. Испытательная версия сайта использует свою базу и тестовые ключи. [Транзакции Django](https://docs.djangoproject.com/en/5.2/topics/db/transactions/) · [Резервные копии PostgreSQL](https://www.postgresql.org/docs/current/backup.html)

## Данные магазина

- `Product` описывает товар. `ProductVariant` хранит продаваемый вариант и его артикул — уникальный код, цену, валюту и остаток. Даже у товара без размеров или цветов может быть один вариант. Для денег использовать точные десятичные значения.
- `Order` хранит номер, покупателя, сумму, валюту и данные доставки. `OrderItem` фиксирует название, артикул, количество и цену на момент покупки. Изменение каталога не должно менять старый заказ.
- `Payment` хранит состояние оплаты и идентификатор операции у провайдера. Состояние оплаты и состояние доставки ведутся отдельно. Номер карты и защитный код остаются у платёжного провайдера.
- Остатки и резервирование обновляются транзакцией — группой операций, которые выполняются целиком или отменяются целиком. При резервировании нужно определить срок и освобождать товар после неоплаты. База проверяет уникальность артикула, номера заказа и идентификатора платёжного события. Проверка доступа к заказу выполняется на сервере для каждого покупателя.

## Возможные этапы магазина

Эти этапы описывают будущий магазин. Их порядок можно уточнить после выбора товаров и рынка.

| № | Что делаем | Как принимаем этап |
| --- | --- | --- |
| 1 | **Сценарии и прототип.** Решить, выходит ли первой версия «журнал + каталог» или сразу магазин. Составить карту страниц и схему данных. Сделать кликабельные макеты главной, каталога, карточки товара, корзины и оформления. | По макету на телефоне и компьютере можно найти товар, увидеть цену, наличие и условия доставки и дойти до подтверждения заказа. Утверждён внешний вид основных страниц. |
| 2 | **Подготовка к публичному запуску.** Разделить настройки для компьютера и хостинга. Поднять испытательную версию с PostgreSQL, шифрованным соединением HTTPS, секретами вне Git и автоматическими проверками. Настроить резервные копии и восстановление. | Проверки Django для хостинга проходят. Сайт открывается по HTTPS. Резервная копия восстановлена в отдельную базу, результат записан. |
| 3 | **Журнал и витрина.** Внедрить утверждённый дизайн, каталог, категории, карточки товаров, поиск и фильтры по нужным свойствам. Настроить публикацию товаров из панели и оформление страниц для поисковых систем. | Редактор публикует товар с фотографиями. Покупатель видит его цену, вариант, наличие и условия покупки на телефоне и компьютере. Вариант «журнал + каталог» можно выпустить после защитных проверок этого объёма. |
| 4 | **Учётные записи и права.** Добавить восстановление пароля, подтверждение почты и ограничение попыток входа. Настроить отдельные роли администратора и редактора, двухфакторный вход для сотрудников и историю изменений. | Автотесты подтверждают права гостя, покупателя, редактора и администратора. Покупатель получает только свои данные. Административные действия отражаются в журнале. |
| 5 | **Корзина и заказы.** Добавить расчёт цены на сервере, доставку или самовывоз, фиксацию состава заказа, резервирование и подтверждение заказа. | Два покупателя не могут одновременно купить последний экземпляр. Повторная отправка формы не создаёт второй заказ. Отмена освобождает резерв. |
| 6 | **Оплата и возвраты.** Выбрать провайдера после определения страны продаж, валюты и способов оплаты. Подключить готовую страницу оплаты провайдера и подписанные уведомления на сервер. | В тестовом режиме проходят успешная оплата, отказ, отмена и возврат. Повторное уведомление не меняет остаток повторно. Система отдельно сверяет сумму, валюту и соответствие операции заказу. [Пример серверного подтверждения оплаты](https://docs.stripe.com/checkout/fulfillment) |
| 7 | **Проверка перед запуском.** Пройти покупки с телефона и компьютера, проверить доступность с клавиатуры, восстановление базы, ошибки оплаты и доставку писем. Подготовить контакты, условия покупки, доставки, возвратов и обработки данных для выбранного рынка. | Выполнена контрольная покупка на испытательной версии. Назначены ответственные за заказы, возвраты и сбои. Подготовлены инструкции обновления и возврата на предыдущую версию. |

После каждого этапа проверяем результат, фиксируем важные изменения коммитом и согласуем следующий этап.

## На что обратить внимание в дизайне

Рекомендуемое направление — спокойная витрина с узнаваемой шапкой OldSchool Journal, одним цветом для действий, читаемыми заголовками и фотографиями товаров. На карточке в первую очередь видны цена, вариант, наличие и действие. Перед подтверждением заказа покупатель видит полную сумму и стоимость доставки. Журнал и каталог связаны навигацией, чтобы читатель мог перейти к релевантным товарам.

В прототипе отдельно проверить размеры текста, заметность клавиатурного фокуса, понятные подписи и ошибки форм, состояния «нет в наличии» и «корзина пуста». Ориентир для доступности — WCAG 2.2 уровня AA, требования к доступности веб-страниц. [Рекомендации W3C](https://www.w3.org/TR/WCAG22/)

## Защита перед публикацией

- Обычный режим разработки рассчитан на `localhost` и включает отладку. [Испытательный профиль](STAGING.md) отключает отладку и требует точные имена сайта, HTTPS, защищённые файлы cookie сеанса и отдельный случайный секрет Django. Повторить `manage.py check --deploy` с настройками хостинга. [Чек-лист Django](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/)
- Сохранять встроенную защиту Django для форм. На сервере проверять владельца заказа, допустимые переходы статуса, цену из каталога и права на административное действие. Для загрузки фотографий ограничить размер и тип файлов, а для журналов и резервных копий — доступ. [Стандарт проверки защиты OWASP ASVS](https://asvs.owasp.org/)
- Перед включением оплаты протестировать подделанное и повторное уведомление провайдера, неверную сумму и одновременную покупку последнего экземпляра. Подтверждать оплату после проверки серверного уведомления, потому что страница возврата покупателя может открыться отдельно от успешной операции. [Подтверждение оплаты на сервере](https://docs.stripe.com/checkout/fulfillment)
- В опубликованной истории старой версии Rails найден ключ погоды в исходном коде. Если он ещё действующий, его нужно отозвать и выпустить новый. Django получает ключ из переменной окружения `OPENWEATHER_KEY`.

## Решения для первого этапа

Перед утверждением макетов нужно определить первую версию сайта, тип товаров, страну и валюту продаж, доставку или самовывоз, наличие вариантов и возможность покупки без аккаунта. Для первого релиза с оплатой разумный старт — один регион, одна валюта, один способ доставки и один платёжный провайдер. Это уменьшает число сценариев, которые нужно проверить до первого заказа.
