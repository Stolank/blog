# Испытательная версия OldSchool Journal

Испытательная версия — отдельный запуск сайта для проверок перед публикацией. Профиль `journal.settings_deploy` выключает подробные сообщения об ошибках, требует отдельный секрет Django и подключается к PostgreSQL. Обычный запуск для разработки описан в [README](../README.md). На Windows все компоненты стенда можно запустить без WSL.

## 1. Подготовить базу и параметры

Создайте в PostgreSQL отдельную базу для стенда, например `osj_stage`, и пользователя с доступом к этой базе. Пользователю сайта не нужны права администратора сервера, создания других пользователей или баз. Для учебного стенда пользователь может быть владельцем своей базы, чтобы Django мог создать таблицы.

Если на Windows используете переносимый архив PostgreSQL, распакуйте программу в путь из латинских букв, например `C:/Users/<имя>/pg-test`. В проверке `initdb` завершался ошибкой кодировки при запуске из пути с кириллицей. [Отчёт PostgreSQL об ошибке](https://www.postgresql.org/message-id/16926-e4ef345545d185ab%40postgresql.org)

Перед командами Django и запуском Waitress задайте переменные окружения — параметры, которые операционная система передаёт процессу. В PowerShell используется `$env:ИМЯ = "значение"`, на Mac — `export ИМЯ="значение"`. Секретные значения загрузите из менеджера секретов или введите в текущей сессии без записи в историю команд. На хостинге используйте его настройки секретов.

| Переменная | Назначение |
| --- | --- |
| `DJANGO_SETTINGS_MODULE` | `journal.settings_deploy` |
| `DJANGO_SECRET_KEY` | Отдельный случайный секрет подписи Django. Сгенерируйте командой `python -c "import secrets; print(secrets.token_urlsafe(64))"` и сохраните как пароль. |
| `DJANGO_ALLOWED_HOSTS` | Точные имена сайта через запятую. Для локального стенда — `127.0.0.1`. Указываются без схемы и порта. |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | Имя базы стенда, пользователь и его отдельный пароль. |
| `POSTGRES_HOST`, `POSTGRES_PORT` | Адрес и порт PostgreSQL. Порт по умолчанию `5432`. |
| `POSTGRES_SSLMODE`, `POSTGRES_SSLROOTCERT` | По умолчанию `verify-full` проверяет сертификат и имя сервера PostgreSQL. Укажите путь к сертификату удостоверяющего центра, если его предоставил хостинг. Для проверки через `127.0.0.1` или `::1` можно явно указать `disable`. |

Храните пароли, закрытые ключи сертификатов, дампы и данные стенда вне Git. Для временных файлов в корне репозитория предусмотрена игнорируемая папка `.staging-local`.

## 2. Запустить Django и HTTPS

Выполните из `blog/django_blog` с активированным окружением Python проекта. `collectstatic` собирает файлы оформления, которые затем раздаёт WhiteNoise.

```sh
python -m pip install -r requirements-deploy.txt
python manage.py check --deploy --fail-level ERROR
python manage.py migrate --noinput
python manage.py collectstatic --noinput
python -m waitress --listen=127.0.0.1:8080 --trusted-proxy=127.0.0.1 --trusted-proxy-headers=x-forwarded-proto journal.wsgi:application
```

Waitress принимает запросы к Django на адресе текущего компьютера. Caddy принимает HTTPS (шифрованное соединение между браузером и сайтом) и передаёт Waitress только запросы с ожидаемым именем сайта. Настройки доверия к Caddy рассчитаны на закрытый внутренний порт Waitress.

В другом терминале укажите `STAGING_TLS_CERT` и `STAGING_TLS_KEY` — абсолютные пути к сертификату и закрытому ключу в формате PEM. На Windows в этих путях используйте прямые косые черты. Для локального прогона можно создать сертификат с помощью OpenSSL. Выполните команду в папке для временных файлов, исключённой из Git.

```sh
openssl req -x509 -newkey rsa:2048 -nodes -days 1 -subj "/CN=127.0.0.1" -addext "subjectAltName=IP:127.0.0.1" -keyout local.key -out local.pem
```

Из папки `blog/django_blog` запустите:

```sh
caddy validate --config deploy/Caddyfile.local --adapter caddyfile
caddy run --config deploy/Caddyfile.local --adapter caddyfile
```

В третьем терминале проверьте `curl --cacert /путь/к/local.pem https://127.0.0.1:8443/`. В PowerShell используйте `curl.exe`. Параметр `--cacert` задаёт доверие к локальному сертификату только для этого запроса.

## 3. Проверить резервную копию

Дамп — файл, из которого можно восстановить таблицы и записи. Подключение команд ниже задаётся переменными `PGHOST`, `PGPORT`, `PGUSER` и, для сервера с проверкой сертификата, `PGSSLMODE=verify-full` и `PGSSLROOTCERT`. Команды могут запросить пароль. Используйте `pg_dump` и `pg_restore` той же основной версии, что и сервер. Сохраните копию в защищённой папке вне Git.

Сначала создайте пустую базу `osj_restore` и дайте пользователю восстановления права на неё. Проверьте имена баз перед выполнением команд. `--single-transaction` применяет восстановление целиком или отменяет его при ошибке.

```sh
pg_dump -Fc --no-owner --no-privileges -f osj-stage.dump osj_stage
pg_restore --exit-on-error --single-transaction --no-owner --no-privileges -d osj_restore osj-stage.dump
```

Временно укажите `POSTGRES_DB=osj_restore`. Выполните `python manage.py migrate --check`. Через Django прочитайте пробную статью и сравните количество нужных записей со стендом. Верните `POSTGRES_DB` на базу стенда.

## Перед публичным запуском

- Выбрать хостинг и домен. Настроить публичный сертификат, перенаправление с HTTP на HTTPS и проверку имени сайта на внешнем сервере. Проверить подключение с проверкой сертификата PostgreSQL, заголовки и доступность сайта снаружи.
- Проверить решение по HSTS (браузер запоминает требование обращаться к домену по HTTPS). Локальная проверка Django сообщает предупреждение `security.W004`. Перед запуском выбрать срок для публичного домена и повторить проверку.
- Настроить ограничение частоты попыток входа и двухфакторную проверку для панели. Повторить проверки гостя, читателя и администратора на хостинге.
- Включить автоматическое резервное копирование и ограничить доступ к копиям. Согласовать срок хранения и повторить восстановление на инфраструктуре хостинга.
