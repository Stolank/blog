# Как проверить сайт после изменений

## Django

После подготовки Django на [Windows](../README.md#локальный-запуск-django-на-windows) или [Mac](../README.md#локальный-запуск-django-на-mac) выполните команды из `blog/django_blog`. `check` проверяет настройки, `migrate --check` ищет неприменённые миграции, а `makemigrations --check --dry-run` проверяет, что модели и файлы миграций соответствуют друг другу.

```powershell
..\.venv\Scripts\python.exe manage.py check
..\.venv\Scripts\python.exe manage.py migrate --check
..\.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
..\.venv\Scripts\python.exe manage.py test
```

На Mac используйте `../.venv/bin/python` в каждой из этих команд. Тесты проверяют публичные страницы, регистрацию, вход, выход и права доступа. Также проверяется, что Django отклоняет отправку формы без токена, который подтверждает, что форму выдал сам сайт. Пробные записи создаются в отдельной тестовой базе.

### Автоматические проверки на GitHub

Проверка **Django checks** запускается после отправки коммитов в ветку `codex/oldschool-journal-django` и в запросах на слияние, где эта ветка указана как целевая. GitHub запускает Python 3.12 на отдельной машине, устанавливает библиотеки, проверяет настройки и наличие миграций, создаёт свежую базу SQLite и запускает автотесты. Миграции — файлы, которые описывают изменения таблиц.

Результат появится во вкладке **Actions** репозитория после отправки файла проверки. Если проверка завершилась ошибкой, откройте **Tests and migrations (SQLite)** и разверните шаг с ошибкой. Если ошибка на шаге **Check for missing migrations**, проверьте, добавлен ли в коммит файл миграции для изменённых моделей. Первая версия проверки использует SQLite. Проверки PostgreSQL описаны в разделе про испытательную версию. [Конфигурация проверки](../.github/workflows/django.yml)

Файл конфигурации прошёл проверку `actionlint`. Команды повторены локально на чистой копии Django с отдельным окружением Python и новой базой. Все миграции применились и 23 теста прошли. Первый запуск в GitHub Actions предстоит после отправки ветки.

После запуска сервера откройте [главную страницу Django](http://127.0.0.1:8000). Пройдите по ссылкам «Статьи» и «Города» и вернитесь через меню. При новой базе оба списка покажут сообщение об отсутствии записей.

| Кто проверяет | Действие и ожидаемый результат |
| --- | --- |
| Гость | Открывает списки записей. При попытке открыть `/admin/` видит вход для администратора. |
| Читатель | Регистрируется, входит по почте, обновляет страницу и выходит. Ссылка «Управление» отсутствует. Повторная регистрация с той же почтой показывает ошибку. |
| Администратор | Входит по имени пользователя, открывает «Управление» и может добавить, изменить и удалить тестовую статью и город. |

Для проверки погоды запустите сервер без `OPENWEATHER_KEY`. В разделе «Погода» введите город и убедитесь, что показаны название и отметка о демонстрационных данных. На `/api/v1/weather/?city=Almaty` должна быть отметка `"демо": true`. Автотесты проверяют обработку ответа OpenWeather на подставных данных, а также поиск, разбиение на страницы и вложенные комментарии.

### Редизайн журнала

В браузере Codex на Windows проверены главная, список и отдельная статья на временной базе. На широком экране открылись обложка и свежие статьи. При ширине окна 390 пикселей все три страницы открылись без горизонтальной прокрутки. Из главной удалось перейти к списку, открыть полный текст и вернуться обратно. Автотесты проверяют в том числе выбор трёх последних статей, поведение пустой базы и безопасный вывод текста. Рабочая база для проверки в браузере не использовалась.

### Первый выпуск

На Windows во временной базе администратор сохранил три пробные статьи через панель и открыл одну по ссылке «Смотреть на сайте». После выхода все три статьи были видны на главной и в списке. Проверены переход к полному тексту и возврат к списку. Читатель вошёл, открыл прямой адрес формы добавления статьи и попал на форму входа в панель.

При выключенной отладке пустой адрес статьи по номеру `999` показал страницу «Страница не найдена» со ссылкой на список. Автотесты проверяют код ответа 404 для отсутствующих страниц, ссылку из панели и доступ к новой статье без входа.

### Черновики и публикация

После введения статуса черновика на отдельной базе SQLite проверили, что старая статья после миграции сохранила адрес, текст и дату. В браузере администратор сохранил черновик, получил ответ 404 по его будущему адресу, затем выполнил действие публикации и открыл статью без входа. Автотесты проверили, что черновики скрыты от гостя и читателя на главной, в списке, по прямому адресу и в ответах API. Повторная публикация сохраняет дату, а пользователь с правом только просмотра опубликовать статью не может.

## Восстановленная версия Rails

Сначала выполните [подготовку Rails из README](../README.md#локальный-запуск-rails). Команды ниже запускайте из папки `blog`. Тестовая база Rails хранится в `storage/test.sqlite3`, отдельно от базы локального сайта.

## 1. Проверить маршруты и загрузку классов

```text
bundle _2.7.1_ exec ruby bin/rails routes
bundle _2.7.1_ exec ruby bin/rails zeitwerk:check
```

Первая команда показывает, какая часть кода отвечает за каждый адрес. Вторая проверяет, что Rails находит классы по именам файлов и может их загрузить.

## 2. Запустить автотесты

Начните с главной страницы, старого адреса входа и прав доступа к панели. Эти проверки затрагивают изменения, сделанные при восстановлении.

```text
bundle _2.7.1_ exec ruby bin/rails test test/controllers/pages_controller_test.rb test/controllers/sessions_controller_test.rb test/controllers/admin/dashboard_controller_test.rb
```

В проекте есть два набора тестов. `bin/rails test` запускает проверки из `test/`. `rspec` запускает проверки из `spec/` с помощью отдельной библиотеки RSpec. Системные тесты в `test/system/` запускаются отдельно и требуют браузера.

```text
bundle _2.7.1_ exec ruby bin/rails test
bundle _2.7.1_ exec rspec
bundle _2.7.1_ exec ruby bin/rails test:system
```

## 3. Пройти сценарии в браузере

После запуска сервера откройте [локальный сайт](http://127.0.0.1:3000).

| Кто проверяет | Действие и ожидаемый результат |
| --- | --- |
| Гость | Открыть главную, статьи и города. Списки доступны. При переходе в `/admin/dashboard` открывается форма входа. |
| Читатель | Зарегистрироваться, выйти, снова войти и обновить страницу. Вход сохраняется при обновлении, а админ-панель остаётся закрытой. |
| Читатель | Попробовать войти с неверным паролем и зарегистрировать тот же адрес повторно. Форма показывает ошибку. |
| Администратор | Войти в учётную запись с ролью `admin`, открыть панель и проверить создание, изменение и удаление пробных статей и городов. |

При сбое запишите команду или адрес, первый текст ошибки и шаг, на котором она возникла. Синтаксическая проверка Ruby проверяет, что файл разбирается как код. Для подтверждения входа и прав выполните шаги с автотестами и браузером.

## Испытательная версия журнала

16 ноября 2026 года на Windows проверен [отдельный стенд](STAGING.md) с PostgreSQL 17.12, Waitress 3.0.2 и Caddy 2.11.9. Сайт слушал только локальный адрес. Секреты и сертификат созданы для прогона.

- Прошли 22 автотеста на SQLite и те же 22 на PostgreSQL. Для второго набора тестовый клиент обращался к Django напрямую. Перенаправление на HTTPS проверено отдельным запросом к запущенному серверу.
- Проверка `check --deploy` завершилась без ошибок, с предупреждением `security.W004` о HSTS. Проверено, что настройки отвергают отсутствующий секрет, произвольные имена сайта и попытку отключить проверку сертификата удалённой PostgreSQL.
- Главная по HTTPS показала пробную статью. Клиент проверил локальный сертификат. Загрузился файл оформления, а запрос с чужим именем сайта отклонён.
- Сервер отклонил отправку формы входа без ожидаемых данных защиты и с чужим источником запроса. Неверный пароль оставил пользователя на форме. После верного пароля выдан защищённый файл cookie сеанса. Гость и читатель перенаправлялись на форму входа при обращении к панели.
- Дамп восстановлен в пустую базу `osj_restore`. Заголовок и текст статьи, число пользователей и число применённых изменений структуры совпали с исходной базой стенда. Django прочитал статью из восстановленной базы, и команда `migrate --check` подтвердила, что все изменения структуры применены. Контрольная сумма обычной SQLite совпала до и после прогона.
